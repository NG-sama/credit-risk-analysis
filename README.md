# Credit Risk Scorecard & Expected Loss Engine

An end-to-end credit risk pipeline built on the HMEQ (Home Equity) loan dataset: exploratory analysis, a WOE/logistic-regression PD scorecard, an XGBoost benchmark, and Expected Loss / IFRS 9 staging — the kind of workflow a bank's credit risk team runs from raw bureau data to a scored portfolio.

Built as a portfolio project for a Credit Risk Analyst application.

## What this does

1. **PD scorecard** — a Weight-of-Evidence-binned logistic regression scorecard (the industry-standard, auditable approach) plus an XGBoost benchmark to quantify the interpretability-vs-performance tradeoff.
2. **Expected Loss** — `EL = PD × LGD × EAD` per account, using a flat LGD assumption and loan balance as EAD.
3. **IFRS 9 staging** — buckets every account into Stage 1/2/3 based on PD level and bureau delinquency/derogatory attributes.
4. **Portfolio aggregation** — Expected Loss rolled up by loan purpose, occupation, and PD band, stored in SQLite for downstream querying.

**Not yet built** (see [Roadmap](#roadmap)): a Claude-powered natural-language query layer over the scored portfolio, and a Streamlit dashboard.

## Business background

| Term | Meaning | Used here as |
|---|---|---|
| **PD** | Probability of Default — likelihood an account defaults | Model output, calibrated to match the true ~20% base rate |
| **LGD** | Loss Given Default — % of exposure lost if default occurs | Flat 45% assumption (standard benchmarking convention) |
| **EAD** | Exposure at Default — balance at risk | Current loan amount (`LOAN`) |
| **EL** | Expected Loss | `PD × LGD × EAD`, the number that drives provisioning |
| **IFRS 9 Stage 1/2/3** | Performing / underperforming / credit-impaired | Cross-sectional proxy from PD + delinquency (see [Limitations](#limitations)) |

## Results

| Model | AUC | KS | Gini | Brier |
|---|---|---|---|---|
| **Scorecard (logistic regression, WOE)** | 0.879 | 0.624 | 0.757 | 0.100 |
| XGBoost (benchmark) | 0.948 | 0.776 | 0.896 | 0.065 |

**Champion: the logistic scorecard.** XGBoost ranks risk better (higher AUC/KS), but the scorecard is chosen for decisioning because every prediction decomposes into a signed coefficient on an auditable WOE bin — that traceability is what a model-risk/validation function needs to sign off on a production credit decision. XGBoost is retained as the challenger; the ~7-point AUC gap is itself a documented finding (the cost of choosing interpretability).

Both models' predicted probabilities are calibrated to the true ~20% default base rate (not class-weighted) — see [Notes on modeling choices](#notes-on-modeling-choices) — since Expected Loss multiplies PD directly into a dollar figure, so this matters more than a small AUC gain would.

Top predictive variables by Information Value (`outputs/metrics/iv_summary.csv`): `DEBTINC` (debt-to-income) and `DELINQ` (delinquent trade lines) are the strongest predictors, followed by `VALUE`, `DEROG`, and `CLAGE` (credit line age).

## Setup

Requires [uv](https://docs.astral.sh/uv/) and Python 3.12+.

```bash
git clone https://github.com/NG-sama/credit-risk-analysis.git
cd credit-risk-analysis
uv sync
```

### Kaggle credentials

The dataset is [HMEQ on Kaggle](https://www.kaggle.com/datasets/ajay1735/hmeq-data/data). Create a `.env` file in the repo root with your Kaggle API credentials:

```
KAGGLE_USERNAME=your_kaggle_username
KAGGLE_API_KEY=your_kaggle_api_key
```

(`.env` is gitignored — never commit it.) If you'd rather skip the Kaggle API, download the CSV manually from the link above and place it at `data/raw/hmeq.csv`.

## Running the pipeline

Each step is idempotent and can be re-run independently; run them in order the first time:

```bash
uv run python -m src.download_data     # -> data/raw/hmeq.csv
uv run python -m src.data_prep         # -> data/processed/hmeq_{binning,benchmark}_input.csv
uv run python -m src.woe_binning       # -> models/binning_process.joblib, outputs/metrics/iv_summary.csv
uv run python -m src.train_scorecard   # -> models/scorecard_logreg.joblib
uv run python -m src.train_benchmark   # -> models/xgb_benchmark.joblib
uv run python -m src.evaluate          # -> outputs/metrics/model_comparison.csv, outputs/figures/*.png
uv run python -m src.expected_loss     # -> data/processed/scored_portfolio.csv, portfolio_el_by_segment.csv
uv run python -m src.db                # -> data/processed/credit_risk.db
```

To rebuild the EDA notebook:

```bash
uv run jupyter nbconvert --to notebook --execute --inplace notebooks/01_eda.ipynb
```

Every script has an assertion-based sanity check on its own output (AUC floors, no NaNs/negative EL, row counts, etc.), so a broken pipeline fails loudly rather than silently producing bad numbers.

## Notes on modeling choices

- **No class-weighting.** HMEQ's ~20% default rate is mild imbalance, and both `class_weight='balanced'` and `scale_pos_weight` were tested — they left AUC essentially unchanged but pushed mean predicted PD to ~28–35% against a true ~20% base rate. Since Expected Loss multiplies PD directly into a dollar figure, that miscalibration would have overstated portfolio loss and skewed IFRS9 staging. Both final models are trained unweighted and calibrate to the true base rate.
- **IFRS 9 staging is a cross-sectional proxy.** HMEQ has no origination date or PD time series, so a real "significant increase in credit risk" (SICR) test — comparing current PD to PD at origination — isn't possible. Staging here uses current PD level plus delinquency/derogatory bureau attributes as a stand-in, and intentionally never uses the realized `BAD` outcome label, to avoid a circular/leaky definition.
- **WOE binning for the scorecard, raw imputed features for XGBoost** — WOE-transforming inputs to a tree model would defeat the point of the benchmark (letting the tree find its own splits on raw data).

## Limitations

- Cross-sectional dataset (no time series) — IFRS9 staging and any concept of "PD migration" are proxies, not the real definitions.
- LGD is a flat assumption (45%), not segment- or collateral-derived — real LGD models use historical recovery data this dataset doesn't have.
- EAD assumes full current balance at risk, with no amortization/prepayment modeling.
